# System-level acceptance criteria

The program is complete only when the lifecycle works as one system, not when its forms or tables exist.

## Required end state

- Users can inspect/revise versioned project models and task position.
- Workers, planners, and reviewers get different immutable, provenance-complete packets; context never silently changes active runs.
- Critical requirements carry source, rationale, scenarios, acceptance conditions, evidence, objective oracles, and explicit coverage.
- Adapters record observable work; workers submit candidates but cannot accept themselves; claims are checked against trace and repository evidence.
- Interruptions recover, and protected merge/release can be blocked for insufficient records or evidence.
- Reviews target immutable revisions and retain anchored, jurisdiction-aware, explicitly dispositioned findings through re-review/escalation.
- Facts, claims, and knowledge remain separate; validated failures become learning candidates and knowledge is versioned, source-linked, disputable, and supersedable.

## Ultimate product test

For every accepted change, Holodeck can answer: why the task existed; which requirements applied; what context each agent received; what the worker did; what failed and recovered; what reviewers found and what changed; which independent evidence proved requirements; who authorized acceptance; and what validated learning was retained.
